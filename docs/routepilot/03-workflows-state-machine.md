# 3. Core User Workflows (Including Concurrency Rules) and the Coverage-Status State Machine

## 3.1 Design principle

**The coverage-status state machine is the single source of truth for a route occurrence's status.** No other component — the SMS system, the risk engine, the dashboard, reporting — maintains its own notion of "is this route covered." Every one of them reads the current status (and the `coverage_events` transition log) and reacts to it; none of them writes status directly except through the state machine's transition function, which validates the transition, records the event, and only then lets side effects (messages, risk recalculation, dashboard refresh) occur.

## 3.2 Coverage status model

| Status | Color | Meaning | Entered from | Exits to |
|---|---|---|---|---|
| `unassigned` | Neutral (gray) | Occurrence exists, no driver identified yet | Occurrence generated by recurrence job | `primary_proposed` |
| `primary_proposed` | Yellow | Dispatcher has identified/invited a candidate driver, awaiting their commitment decision | `unassigned` (dispatcher proposes) | `committed` (accept), `unassigned` (decline/withdraw) |
| `committed` | Green | Driver has accepted the recurring commitment for this occurrence; confirmation checkpoints not yet due | `primary_proposed` (accept) | `confirmation_pending` (checkpoint window opens) |
| `confirmation_pending` | Yellow | A confirmation checkpoint has fired; awaiting driver response | `committed` (checkpoint fires), `confirmed` (next checkpoint fires) | `confirmed` (driver confirms), `at_risk` (deadline passes with no response or driver hesitates), `primary_canceled` (driver declines/cancels) |
| `confirmed` | Green | Driver has explicitly confirmed for this specific occurrence | `confirmation_pending` (driver confirms) | `confirmation_pending` (next checkpoint opens), `primary_canceled` (late cancellation), `completed` (route runs) |
| `at_risk` | Orange | A confirmation deadline passed with no response, or a risk rule flagged the assignment | `confirmation_pending` (no response by deadline), risk engine (rule trigger) | `confirmed` (late response arrives and is accepted), `primary_canceled` (driver cancels), `backup_sourcing` (dispatcher escalates preemptively) |
| `primary_canceled` | Red | Primary driver has explicitly canceled, declined, or been marked a no-show | `confirmation_pending`, `confirmed`, `at_risk` | `backup_sourcing` (system/dispatcher begins recovery) |
| `backup_sourcing` | Orange | System/dispatcher is identifying and has not yet offered to, or is waiting on, backups | `primary_canceled` (auto-enter) | `backup_offered` (offer sent) |
| `backup_offered` | Orange | One or more standby offers are outstanding | `backup_sourcing` (offer sent) | `backup_accepted` (a driver accepts), `backup_sourcing` (all offers expire/decline, re-source) |
| `backup_accepted` | Yellow-green | A backup has accepted; activation pending dispatcher confirmation (or auto-activate if configured) | `backup_offered` (accept) | `recovered` (activation) |
| `recovered` | Green | A backup is now the active driver for this occurrence; route is expected to run | `backup_accepted` (activation) | `completed`, `failed` (backup also fails) |
| `completed` | Neutral (green check) | Route ran to completion (with original primary or a recovered backup) | `confirmed`, `recovered` | Terminal |
| `failed` | Red | Route did not run / did not complete and no recovery occurred in time | `primary_canceled`, `backup_sourcing`, `backup_offered`, `recovered` (backup also failed), `at_risk` (dispatcher marks failed) | Terminal |
| `canceled` | Neutral (gray) | Occurrence itself was canceled (not a driver failure — e.g., customer canceled the delivery) | Any non-terminal status (dispatcher/manager action) | Terminal |

This is 13 statuses — intentionally not more. States like "primary proposed" and "committed" are collapsed rather than split further (e.g., no separate "invitation sent" vs "invitation viewed" status — that distinction lives as a timestamp/event, not a status).

### Manual override

- **Dispatcher** can manually transition to any status reachable from the current status per the transition table, and can force-transition to `canceled` from any non-terminal status (route/customer-level cancellation always wins).
- **Branch Manager/Administrator** can additionally force any transition (e.g., correcting a dispatcher error), but every manual override is logged with actor, timestamp, previous status, new status, and a required reason note — manual overrides are a first-class audit event, not a silent edit.
- No role can bypass the transition table's validity check — an "override" still goes through the same `transition()` function; it just carries an `is_manual_override: true` flag and a note, and a broader set of allowed target states.

### Invalid transitions

Any event that would move an occurrence to a status not reachable from its current status per the table above is **rejected, not silently ignored**: it is written to `coverage_events` with `accepted: false` and a `rejection_reason`, so it's visible in the audit trail and debuggable, but the occurrence's actual status does not change. Example: an inbound SMS "YES I'll be there" arrives for an occurrence already in `completed` — this is logged as a rejected/out-of-context event (see §3.4 race conditions) and routed to the dispatcher's needs-review queue rather than applied.

## 3.3 Workflow-by-workflow detail

### Program setup

1. Branch Manager creates a recurring delivery program → creates `delivery_programs` record.
2. Manager creates one or more route templates → `route_templates`.
3. Manager defines recurrence and route requirements → `route_recurrence_rules`, `route_requirements`.
4. Manager adds disclosure information (stops, pay, duration, vehicle/qualification needs, any customer-specific terms) → fields on `route_templates`.
5. Manager defines driver qualifications required → linked `qualifications` records via `route_requirements`.
6. Manager defines confirmation timing (e.g., day-before at 6pm, same-day at 5am) → `checkpoint_schedule_config` on the template.
7. Manager defines backup requirements (how many backups desired, standby compensation default) → fields on template/program.
8. System generates future route occurrences → scheduled job reads recurrence rules, inserts `route_occurrences` for a rolling window, each starting in `unassigned`.

- Automated actions: occurrence-generation job (idempotent — re-running for an already-materialized week produces no duplicates, keyed on `(route_template_id, occurrence_date)`).
- Notifications: none yet (no driver assigned).
- Edge cases: recurrence rule edited after occurrences already generated (future occurrences regenerate/update; past/near-term occurrences already committed are not silently altered — manager is warned and must explicitly propagate changes).
- Required records: `delivery_programs`, `route_templates`, `route_requirements`, `route_recurrence_rules`, `route_occurrences`.

### Driver commitment

1. Dispatcher identifies a potential driver (manually, from driver list filtered by qualifications) → no write yet.
2. Driver receives full route disclosure (SMS with link to disclosure web page) → `outbound_messages` record, `driver_commitments` record created in `proposed` state.
3. Driver reviews route details (opens web page — page view logged for the needs-review/troubleshooting picture, not a hard state signal).
4. Driver accepts or declines (SMS keyword or web page button) → `inbound_messages`/web-action event → transition function.
5. Driver agrees to specific recurring dates or recurrence terms → recorded on `driver_commitments` (which occurrences/days this covers).
6. System records the commitment → `driver_commitments.status = accepted`, timestamped.
7. Driver is assigned as primary or backup → `assignments` record created; occurrence transitions `unassigned → primary_proposed → committed` (or added to a backup pool without a status transition on any specific occurrence, since backups aren't tied to occurrence state until activated).

- User actions: dispatcher selects/invites; driver accepts/declines.
- Automated: disclosure message send, state transition on response.
- Notifications: driver receives disclosure; dispatcher receives accept/decline notice.
- Edge cases: driver accepts one occurrence's terms but the recurrence spans a date range the driver wants to modify (e.g., "I can do Mon/Wed but not Fri") — recorded as a partial commitment, not auto-accepted at template scope.
- Failure scenarios: driver never responds to disclosure → invitation expires after a configured window, occurrence stays `unassigned`, dispatcher is prompted to try another candidate.
- Required records: `driver_commitments`, `assignments`, `outbound_messages`, `inbound_messages`, `coverage_events`.

### Confirmation

1. System schedules confirmation checkpoints → `confirmation_checkpoints` rows created at template-configured offsets when an occurrence reaches `committed`.
2. Driver receives a confirmation message → scheduled job fires at the checkpoint's due time, sends SMS, transitions occurrence to `confirmation_pending`.
3. Driver confirms, declines, or does not respond → inbound message/timeout.
4. System updates coverage status → `confirmed`, `primary_canceled`, or (on timeout) `at_risk`.
5. Risk rules evaluate the response → risk engine re-scores on every checkpoint event (see `06-risk-engine.md`).
6. Dispatcher receives an alert when action is required → dashboard + optional SMS/email digest for `at_risk`/`primary_canceled`.

- Edge cases: driver responds after the deadline has already passed and the occurrence auto-transitioned to `at_risk` (see race conditions, §3.4).
- Failure scenarios: messaging provider outage during a checkpoint window — job records a delivery failure, retries per policy, and if still undelivered by the deadline, treats it as equivalent to no-response but flags it distinctly in the audit log ("no-response due to delivery failure" vs. "no-response, delivered") so the dispatcher and reporting don't unfairly count it against driver reliability.
- Required records: `confirmation_checkpoints`, `confirmation_responses`, `coverage_events`, `risk_assessments`.

### Recovery

1. Driver cancels, declines, or becomes unresponsive → occurrence transitions to `primary_canceled`.
2. Dispatcher records or receives the cancellation reason → reason code required to complete the transition (driver-given via SMS keyword, or dispatcher-entered).
3. System identifies qualified backup drivers → hard-requirement filter + preference ranking, run synchronously so the dispatcher sees candidates immediately on the same screen that shows the cancellation.
4. Standby or replacement offers are sent → `standby_offers` created, occurrence → `backup_sourcing` → `backup_offered`.
5. Backup accepts → first acceptance wins (see race conditions); `standby_offers.status = accepted` for the winner, `expired`/`superseded` for the rest.
6. Dispatcher activates the backup (or auto-activates if the program is configured for auto-activation) → occurrence → `backup_accepted` → `recovered`.
7. Coverage status changes to recovered → dashboard reflects immediately.
8. All actions are logged → `coverage_events`, `audit_logs`.

- Edge cases: no qualified backup available → occurrence stays in `backup_sourcing`, dispatcher gets an escalation prompt to widen criteria or source manually outside the pool; if departure time passes with no recovery, occurrence auto-transitions to `failed` (or dispatcher marks it).
- Required records: `cancellation_reasons` (linked), `standby_offers`, `assignments`, `coverage_events`.

### Completion

1. Route is marked completed, failed, canceled, or no-show → dispatcher action or (for completed) an optional automatic default if no issue was reported by end of day, per program configuration.
2. Driver reliability history is updated → aggregate fields on `drivers` (or computed on read from `route_outcomes` + `coverage_events` — recommend computed-on-read for MVP to avoid drift).
3. Route outcome is added to reporting → `route_outcomes`.
4. Risk indicators are recalculated → next occurrence's risk assessment incorporates the new outcome.

## 3.4 Concurrency and race-condition rules

Every rule below is enforced by making the state-machine transition function the only writer of status, using a database-level optimistic concurrency check (a version/updated-at column compared-and-swapped on write) so two simultaneous writers can't both "win" silently.

1. **Two dispatchers act on the same route at the same time** (e.g., both click "cancel" or one cancels while the other assigns a backup).
   - Rule: first write wins (by database transaction commit order); the second dispatcher's action is evaluated against the *now-current* status, not the status they last saw on screen. If it's no longer a valid transition from the new current status, it's rejected with a clear UI message ("This route was already updated by [other dispatcher] — refresh to see the current status") rather than silently overwritten or silently applied on stale data.
   - Message to affected parties: no driver-facing message; the losing dispatcher sees an in-app conflict notice.

2. **A backup accepts a standby offer moments after the primary un-cancels or re-confirms.**
   - Rule: the primary's re-confirmation takes precedence if it lands before the backup's acceptance is *activated* (not just received) — because activating a backup while the primary is genuinely available creates double coverage and driver-trust damage. Concretely: if primary re-confirms while occurrence is still `backup_sourcing`/`backup_offered` (backup not yet accepted/activated), occurrence returns to `confirmed` and all outstanding standby offers are auto-canceled. If the backup has already been activated (`recovered`) before the primary's re-confirmation arrives, the backup stays primary for this occurrence (you don't yank a driver who already committed to cover), and the original primary is notified their route is already covered and, if desired, offered the *next* occurrence instead.
   - Message: to the primary — either "You're confirmed, thanks" or "This route was already covered by a backup for this date — you're still committed for future occurrences" depending on timing. To the backup — "Your standby offer was canceled, the original driver is confirmed" (case A) or a normal activation confirmation (case B).

3. **A driver replies to an old message after the route state has changed.**
   - Rule: every outbound message carries a reference to the specific `(occurrence_id, checkpoint_id or offer_id)` it was about. An inbound reply is matched to the most recent *open* (unanswered) outbound message to that phone number if one exists; if the referenced context is already resolved/terminal, the reply is logged against that old context but does **not** trigger a state transition — it's routed to the needs-review queue with a note ("reply to a resolved thread from [date]") so a dispatcher can glance at it and decide if it needs a manual reply, but nothing changes automatically.
   - Message: driver gets a brief auto-response only if there's no ambiguity risk — e.g., "That route has already been resolved — a dispatcher will reach out if anything's needed." (Optional; can also be silent in MVP to avoid overpromising a response.)

4. **A confirmation response arrives after the checkpoint window closed.**
   - Rule: the checkpoint has a hard deadline; a job transitions unanswered occurrences to `at_risk` at the deadline. A late response arriving after that point is accepted as a status-improving signal (moves `at_risk → confirmed`) *if* the occurrence hasn't already been escalated further (e.g., already `primary_canceled` because the dispatcher acted on the risk in the meantime) — in that case it's logged but does not override the dispatcher's already-taken action; it's flagged for the dispatcher to see and confirm what to do next.
   - Message: driver gets "Thanks, you're confirmed" if accepted, or "This route already moved to backup coverage — a dispatcher will follow up" if not.

5. **The same standby offer is sent to multiple drivers and more than one accepts.**
   - Rule: strictly first-accept-wins, enforced by a unique partial index / row-level lock on "one active-winner per occurrence" at the database layer, not just application logic (so two near-simultaneous webhook deliveries can't both win). The first accepted response transitions the offer to `accepted` and the occurrence to `backup_accepted`; every other outstanding offer for that occurrence is atomically set to `superseded` in the same transaction.
   - Message: winner gets an activation/confirmation message with route details. Every other driver who accepted (or accepts within seconds after) gets "Thanks for responding — this route was already covered by another driver. We'll keep you in mind for the next opportunity," immediately, not at the end of a batch job.

General rule across all five: **the database transaction, not application timing, decides the winner**, and every affected party always gets a message reflecting the actual final state — nobody is left believing they have a route they don't, or told "not required" when they in fact are.
